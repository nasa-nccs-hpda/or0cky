"Our best chained step" = the D175 configuration (also what the untracked `model_driver.ModelDriver(surface="closed", ent="computed", rng="chain", daily=...)` wraps). It is a NumPy/Python orchestration that calls JAX kernels per stage (`atm_step.run_step`, `surface_loop_v2.Loop2.stage_surface`); state lives in dicts of NumPy arrays between every stage; several modules are re-bound at run time ("monkey-patched" for the duration of a step in `model_driver._patched`).

Terms for the implementation column: **FORT** = original Fortran (radiation server only); **REC** = recorded input read from a real-model dump; **NP** = NumPy / plain Python (including per-cell Python loops); **EJ** = eager JAX (op-by-op dispatch, no outer jit, arrays converted to/from NumPy around calls); **JJ** = jitted JAX.

## 1. Coverage matrix: one coupled step of P2SAoM40 in the order of the real main loop

Grid: IM=72, JM=46, LM=40 atmosphere layers, LMO=13 ocean layers, atmosphere arrays mostly `(IM,JM,LM)` float64 with `(LM+1,IM,JM)` for edges (PEDN, SRHR, TRHR) and `(LM,IM,JM)` for MA/PK/PMID in radiation code; surface state as `(IM,JM)` or `(IM,JM,k)` dicts; ocean state `(IM,JM,LMO)` (transposed from the restart) [code: `surface_loop.load_restart`, `atm_step.radia_apply`, `surface_loop.py:27`]. All float64 (`jax_enable_x64`); the radiation packet is 52 fields (D155) of float64 arrays; two tile-record sets of float64 rows (see 1.4).

Real order (MODELE.f main loop, ATM_DRV.f; as in `model_driver.py` docstring [code] and D164 section 1): `startNewDay` (diagnostics) -> **atm_phase1** (DYNAM+QDYNAM+energy fix, MELT_SI, CONDSE, RADIA) -> **PRECIP_SI / PRECIP_OC** -> **SURFACE** (IRRIG_LK, PRECIP_LI, PRECIP_LK, 2 substeps, GROUND_LI, UNDERICE/GROUND_SI/GROUND_LK/RIVERF/FORM_SI for lakes) -> **ocean_driver** (DYNSI, UNDERICE, GROUND_SI, CALC_APRESS, OCEANS, FORM_SI, ADVSI) -> **atm_phase2** (DISSIP, FILTER) -> **clock / daily** (`dailyUpdates` when the step starts a day) -> diagnostics.

Validation vocabulary: "bitwise (numpy-pow)" = bit-identical to our NumPy port, which itself is bitwise to the real model only with the Intel libimf `pow`; "bitwise vs real" = 0 differing elements against the real dumps; "rounding level" = <= 1e-12 of scale (category B of `ACCEPTANCE_CRITERIA.md`).

## 4. State pytree (design)

All device arrays float64 (x64 enabled), grouped so a jitted function receives only what it uses; static data (geometry, tables) are closed over or passed as a separate constant pytree.

```
State = {
  'atm':   {T,U,V,Q,QCL,QCI (IM,JM,LM); P,PS (IM,JM); TMOM,QMOM (moment arrays); MA,PK,PMID,PDSIG,PEDN,PEK,GZ,MUS,MVS,MWS;
            PBL/ATURB hidden: EGCM,W2GCM (LM,IM,JM-ordered as today), PBLHT,DCLEV,PBLPTOP,TSAVG,QSAVG,USTARPBL,LMONINPBL,T1AA,U1AA,V1AA,
            CONDSE/RADIA carry: CLDSS,CLDMC,SNOAGE,RQT,KLIQ,TAUSS,TAUMC, LSCOND module arrays 'ms'; frozen radiation: SRHR,TRHR(LM+1,IM,JM),COSZ1,FSF(4),TRSURF(4),SRVISSURF,FSRDIR},
  'ocean': {g0m,s0m,mo,uo,vo,uod,vod, gx/gy/gz/sx/sy/szmo (IM,JM,13); ogeoz,ogeoz_sv,kpl (IM,JM); straits must,g0mst,... (13,NMST)},
  'ice':   {rsi,snowi,msi,pond_melt,flag_dsws (IM,JM); hsi,ssi (IM,JM,4); RSIX,RSIY, USI,VSI},
  'lake':  {mwl,gml,tlake,mldlk,T2Lbot}, 'landice': {snowli, tlandi},
  'land':  {GHY w,ht,nsn,dzsn,wsn,hsn,fr_snow (per cell, padded to fixed sizes), PBL tile carry (u,v,t,q,e profiles per type), Ent state (1023 doubles/cell padded)},
  'rng':   {seed0 (uint32 scalar)},
  'clock': {itime (int), day index}

```
Two representation decisions that gate everything else:
1. **Fixed-shape tiles.** Replace the per-step record rowsets (rows change with ice tiles) by a fixed `(type, IM, JM)` layout with a validity mask (4 types x 3312 cells); the "template builder" of D174 becomes a one-time static-field builder. Without this no PBL/tile/GHY stage can sit in one jit.
2. **Land as a padded batch.** 753 land cells with GHY and Ent per cell: a masked fixed-trip loop (sub-iterations bounded; D158 shows >= 12 occur) with the state as padded arrays. This is a port of Ent (not existing in JAX) and of the closed-loop GHY+Ent coupling; it is the largest new-code item (README estimates Ent water/energy side alone 9-14 h of agent work for the NumPy side; batched JAX Ent 15-25 h).

## 5. Design of the JAX-driven coupled step

### 5.1 What goes inside one jit and where the boundaries must be

Planned structure (the aim is 4 jitted functions per step, plus 1 host callback; the minimum number of host-device transfers is one state `device_put` at start and one `device_get` at the end of the run, plus the radiation packets):

| Jit unit | Contents | Rows | Why this boundary |
|---|---|---|---|
| J1 `phase1a` | pre-dynamics bookkeeping, DYNAM (5 passes), MELT_SI, CONDSE (LSCOND, MSTCNV, post-processing), up to the radiation packet assembly | 2-7 | all pure array code once TROP/MAtoPMB/z-extra/ADV1D subsidence are moved to JAX and the libimf question (5.2) is settled |
| host callback `radia` (every 5th step) | build packet (device -> host), persistent server call, packet returned (host -> device) | 8 | Fortran cannot be inside a jit; use `jax.experimental.io_callback` (ordered, side-effecting) inside the jit (keeps one jit) or end J1 and start J2 around a Python call (simplest, 2 explicit syncs). Decision for the first build: the Python-call variant with explicit logged `device_get`/`device_put`; evaluate `io_callback` afterwards |
| J2 `phase1b_surface` | RADIA apply, radiation-derived columns, PRECIP_SI/OC/LI/LK, TOC2SST, both SURFACE substeps (PBL, ATURB, tiles, land GHY+Ent, land ice), GROUND_*, RIVERF, DYNSI, ocean (OCEANS), FORM_SI, ADVSI | 9-23 | the whole surface+ocean stage in one function: ocean and surface state are independent of the atmosphere of the same step except through the fluxes (D175 note); `lax.scan` over the 2 substeps and over the 5 ocean/odiff sub-passes as the plan dictates |
| J3 `phase2` | DISSIP, FILTER, MAtoPMB, PEK, carry assembly | 24 | needs the same libimf decision as J1 |
| host (outside jits) | day-boundary updates (drv_daily), clock, checkpoint, recorded-input provider (loads constant-per-date data and, for the first step, the step's template statics once), logging | 1, 25 | single step crosses no day boundary; multi-day can call `drv_daily` on the host once per 48 steps (a small, reported device_get/put) |

Per radiation step the transfer volume is the packet (T, Q, PK, PMID, PDSIG, PEDN, MA, cloud arrays: about 30 arrays of 132k doubles = ~35 MB in) and the outputs (~55 MB out, per D155 file sizes of the one-shot server; the persistent server's packets are the same format [code]); about 90 MB per call, i.e. `bytes_in/out` must be logged, not assumed.

If all of J1, J2, J3 are not achieved in the first build, the fallback boundary list (section 6, stages S2-S5) allows partial jits; the result file then states which items of criterion 1 fail. A "JAX-driven" claim is made only when stages S1-S6 have passed.

### 5.2 The libimf question (decides what C1 and C2 can show)

- The NumPy chained step uses the Intel libimf `pow`/`exp` through ctypes (`intel_libm_ff`, per-element scalar calls). This is what gives the bitwise results against the real model (dynamics 18 steps; CONDSE flips in 3-5% of columns otherwise [D127-D129, Handoff]).
- JAX stages are bitwise only against the numpy-pow / libm variants (D144b, D145-D147); JAX dynamics vs libimf-numpy: U differs up to 3.5e-13 relative in most cells [D175 section 4].
- Consequence for the design: two reference chains are needed.
  * **C1 reference (port consistency): the NumPy chained step run in "libm mode"** (`imf=False`: numpy `pow`, libm `exp`; same code, same driver), because that is the only mode against which the JAX kernels were proven bitwise. C1 then compares like with like and can reach category A.
  * **C2 (vs real Fortran) needs libimf semantics.** Options: (a) a JAX `pure_callback` to libimf `pow`/`exp` inside J1/J3 (the "libm mode" of D145 already uses `pure_callback` to the same scalar functions; libimf mode in JAX was never run); this is a host callback (non-device-resident) for those elementwise calls and must be listed as a non-JAX item; (b) accept rounding-level (B/C) results for C2 and say so (the acceptance document already allows: "without libimf the comparison is reported at B or C"; CONDSE threshold flips will then limit the cloud fields in some columns: expected outcome "partly met", based on D127-D129, not yet tested for the JAX path). Recommended first: C1 in libm mode, C2 reported at the level obtained in libm mode, then repeat C2 with (a) as a labelled variant. This is a decision for the owner (open question Q1).

### 5.3 Radiation callback: declaration and logging

Provider interface: reuse the D178 `BoundaryProvider` idea (exists, unverified): `stage_radia(S, R, ctx)`, `radiation_aij`, `surface_records`, `column_modifiers`, `initial_seed`, `daily_inputs`, `state/set_state`. The provider is the single object through which every non-JAX input passes; the JAX-driven step takes a provider with the same interface so that C1 and C2 can swap implementations without editing the step code.
Every result file starts with `result.json`/header fields, written by the driver (not by hand):
- `radiation: "computed by the original Fortran (hybrid component)"` and the same sentence printed above every table/plot produced from the run (generated from the header);
- per call: itime, seed, packet input field list with shapes/dtypes, bytes in/out, server seconds, wall seconds, number of host synchronisation points; totals for the run; `server_binary`, restart used, `SOCRATES_modified: false`;
- whether radiation was Fortran-served or recorded (record replay is a different, labelled mode: "radiation replayed from the real record").

### 5.4 Recorded inputs: declaration and logging

A recorded input is any array read from a real-model dump or restart that the step does not compute. The provider keeps a registry `recorded[name] = (source_file, bytes, step_range, used_in_stage)`; every read goes through `provider.get(name)`; at the end the driver writes `recorded_inputs.json` and a summary line to the result (number of recorded items, total bytes), and **fails the run if a read happens that is not in the declared list** (as required by ACCEPTANCE section 1.5). The initial list is the D174 inventory, updated for D176/D177 (untracked work, to be confirmed):
- template rows and static columns (coriol, hemi, ihc, focean, axyp, soil static, top_index ...), from `ffp/ffs/ffl/ffg/fft` of the step (first step only in the final design after the fixed-shape builder, S1);
- Ent exports in `ent="record"` mode, or none in `ent="computed"` (D171) except the first-step Ent ulp residual and `set_vegetation_data` for a first day (D174, D169);
- hidden first-step atmosphere state (MUS, MVS, MWS, GZ, ATURB hidden fields) from `ffd_state_s1`/`ffa_step_a` of step 0 (all 3 dates);
- `TRUP_in_rad`, MMST (init_STRAITS), the 5 static ADVSI geometry vectors, irrigation demand (reconstructed from the recorded actual flux), radiation-packet surface side 20 fields until D176's `drv_radpacket` is accepted, MDRYA/dH2O/Ca constants per date, `SEEDS[0]` of the first step, the straits start state and the AG2OG/IG2OG items in the replay ocean chain;
- CONDSE entry non-state fields (which are read before written was never tested, D174).
The first coupled step will use the whole D174 list (acceptance open point 3 asks the owner which must be computed first).

### 5.5 Instrumentation for the criteria in section 1 and 6 of ACCEPTANCE_CRITERIA

The driver (new file, not an edit of `model_driver.py`) counts: jit-compiled function calls per step (wrapped call counter), `jax.device_put`/`device_get` calls and bytes (wrapped), number of XLA compilations (`jax.monitoring` or the compile-count approach of D175), per-stage wall time with `block_until_ready`, and writes them to the header. ### 5.6 Validation organisation

Both comparisons are run by one script and report separately (ACCEPTANCE section 2).

**C1 (JAX-driven vs NumPy chained step).**
- Same node, same pinned core set (`taskset -c <same>` for both runs), same thread count (`OMP_NUM_THREADS=1`, `XLA_FLAGS` thread settings identical), because the existing code is NOT reproducible across core counts (1 vs 3 cores: T 1.7e-13, U 8.3e-13 after step 0; 123 of 168 arrays differ after 2 steps) [D175]. The two sides are run as two processes on the same cores (not at the same time), each recording its own `taskset`/thread/flag header.
- XLA flags before importing JAX: `--xla_cpu_max_isa=AVX --xla_disable_hlo_passes=algsimp` (`dyn_jax_env.py`, `clouds_jax_env.py`; the JAX stages in the ocean/GHY/PBL chain used `dyn_jax_env` or none; every module of the JAX-driven path must be imported after the flags; a check `fma_free()` and an algsimp probe are run first and logged).
- No persistent compile cache (`JAX_COMPILATION_CACHE_DIR`, `CLOUDS_JAX_CACHE` unset): a warm cache changed T by 0.067 K after one step [D175]; the driver asserts the variables are unset.
- Reference: NumPy chained step in libm mode (5.2) from the identical start state (the same restart + records) and the same provider records.
- Compare each prognostic field, stage by stage (stage boundary mode: feed the NumPy stage inputs into the JAX stage as D144b did) and the end state of the step. Report per field A/B/C/D with maximum absolute difference over scale; exceptions listed with coordinates (rule of ACCEPTANCE section 3). C1 target: A, with B accepted only where the stage is known to differ by reduction order (ocean per D170 level).
- Mutation tests as in the existing suites (a perturbed input must change the result; protects against a comparison that cannot fail).

**C2 (JAX-driven vs real Fortran).**
- Start from the real restart of each of the three dates (nov26, dec01, jan01); compare the state after step 0 with the real step-boundary dumps (`ffa_step_*`, `ffd_state_s*`, ocean `ffo` tag 14 for the ocean exit, etc.), using the existing F1-gate comparer `atm_step_compare.py` categories A/B/C/D and the exception rule; per date, not pooled.
- Variants labelled in the result: libm mode vs libimf-callback mode (5.2); radiation Fortran-served vs replayed; Ent computed vs recorded; GHY JAX vs recorded land patch (the recorded land patch is MET on all 3 dates; the ported land on nov26 only, partly met on dec01/jan01 [Handoff]). The first coupled-step claim is made for the variant with all computed surfaces and Fortran-served radiation, and the others are reported as controls.
- Surface comparison: ocean/ice/lake/land-ice exit state against the real surface records (the v2 loop does not compare its own surface state with the records in the coupled run: D170 "Not done"); this comparison must be added to the harness (S6).
- Multi-day (F2): same driver, `radiation callback every 5th step`, noise-floor method of D151/D157; unchanged.

## 7. What would NOT be end-to-end JAX in the first coupled step

To be reported in every result, with its measured share (generated by the lint of 5.5):

1. **Radiation:** the real RADIA / SOCRATES in the persistent Fortran server (a separate process; file/pipe protocol; ~11-14 s per call; packets ~90 MB per call; host synchronisation at every 5th step). Standing rule: never ported. Sentence required: "radiation computed by the original Fortran (hybrid component)".
2. **Recorded inputs** (section 5.4): template rows/static columns, the Ent exports (if `ent=record`), hidden first-step atmosphere state, TRUP_in_rad, MMST, ADVSI geometry vectors, irrigation demand (reconstructed from the recorded flux), radiation-packet surface side (until D176 is verified), per-date constants (MDRYA, dH2O, Ca), the first `SEEDS[0]`, the straits start state. Read through the provider, on the host, from files (file I/O).
3. **libimf bridge** (if C2 variant (a) is used): `pow`/`exp` through ctypes callbacks in dynamics, CONDSE and Ent; a host callback per element batch, not device-resident. Without it C2 is at rounding level or worse (5.2).
4. **Ent (vegetation)** until a JAX port exists: scalar Python per cell; in the first build either recorded or NumPy. Same for the per-cell GHY+Ent iteration loop with data-dependent counts if not rewritten as masked fixed-trip loops.
5. **ADVSI** (NumPy + `mpmath` binary128 `Ti2b`) and **RIVERF** (NumPy) until ported; REAL*16 is not representable in device float64 (D173): sea-ice `Ti`/`Ti2b` stay float64 in the jit path (differs from the Fortran at rounding level; GROUND_SI not bitwise either way).
6. **Host glue at jit boundaries:** TROP, MAtoPMB, se/ke/efix and the z-extra column branch of QDYNAM (until converted), the MSTCNV LMIN loop and ADV1D subsidence callback (until converted), `stop_model`-type checks turned into flags read on the host, day-boundary updates (`drv_daily`), clock, seeds, checkpointing, logging.
7. **Compilation and dispatch:** step 0 costs 140-217 s of XLA compilation (1,059 compilations, D175) on this CPU; it is a performance item, not a correctness item, and is reported per ACCEPTANCE section 6.
8. **Hardware:** this node has no GPU (`jax.devices()` = one CpuDevice [probe]). "On device" in the first result means the XLA CPU backend; no accelerator claim can be made. XLA:CPU f64 `exp`/`pow` equal glibc; an accelerator will differ at 1e-16 and flip threshold branches (D145).
9. **Not computed at all (carried over from D174):** daily_LAKE (variable lake fraction), daily_LI, daily_OCEAN/GLMELT, first-day `set_vegetation_data`, Ent carbon/soil (`soil_bgc`), SNOAGE aging inputs (TDIURN), diagnostics beyond the 257+4 F3 columns. A single step does not cross a day boundary, so these do not affect the one-step gate; they limit the multi-day run.
