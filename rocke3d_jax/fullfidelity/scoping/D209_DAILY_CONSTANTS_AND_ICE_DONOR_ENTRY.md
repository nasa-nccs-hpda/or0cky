## 2. Item B: the new-tile donor rule

### 2.1 Where it lives and what it is
Fortran: `loadbl` (`PBL_DRV.f:1098-1237`, called at the start of every SURFACE step, `SURFACE.f:409`, helper `setbl` `PBL_DRV.f:1239`): a surface tile whose `ipbl` is 0 (no PBL call in the previous step, i.e. the tile did not exist) takes the PBL state (u, v, t, q, e profiles, cm/ch/cq, ustar, lmonin) from a donor type of the same cell with ipbl 1: ocean <- ice else land; ice <- ocean; land ice <- land; land <- land ice else ocean; then all `ipbl` are cleared. The rule concerns the persistent PBL state (template columns 51-89 and 34-36 of the ffp rows), not the tile existence itself.
Repo: it is **already implemented in NumPy** (`drv_state_cols.PBLCarry.begin_step`, D177, order of donors `DONORS`), tested bitwise against the records (`tests/test_drv_state_cols.py::test_pbl_carry_bitwise`, 54 steps of nov26 and 6 each of dec01/jan01; re-run in this session: 4 passed). The statement "not implemented" in D191/D193/`jax_coupled.py` refers to the **assembled JAX step**, whose template PBL profile columns are read from the record of every step.

### 2.2 Is it triggered in the nov26 day? Yes (demonstrated; `tile_appearance_census.txt|json|py`, `donor_rule_counts.txt`, `d190_newtile_check_nov26_day.txt`)
Tile appearances between consecutive steps in the recorded ffp rows (54 steps): **8 new ice tiles** (steps 9, 18, 28, 32, 37, 39, 47, 53; cells (22,34), (16,34), (20,34), (51,34), (50,35), (55,33), (20,38), (51,35)), **60 new ocean tiles**, 0 new land-ice or land tiles; 2 ice and 114 ocean tiles vanished. The 8 ice events agree with the D190 count run again.
With the NumPy rule and the carry fed by the recorded outputs, the carried state equals the recorded input columns bitwise at all 68 appearing tiles (and at all 37649 existing ice tiles); with the rule switched off (stale state, only ipbl cleared) all 68 appearing tiles mismatch (`tests/test_d209_newtile_donor.py`, 1 test passed). So the rule is exercised and is needed whenever the template is not taken from the record.
Relation to the earlier mask mismatches: the D193 tile-mask mismatches (ocean/lake-water type, steps 43 and 48-53) are a different issue (tile SET from MELT_SI/RSI); they were traced to daily_LAKE (D196) and removed by D205 apart from the single step-53 cell. They are not the donor rule, and the donor rule cannot change them (the template tile set is recorded).

### 2.3 What is NOT done, and why it was stopped there
The JAX assembled step does not use the rule, because the recorded template already contains the donor-initialised columns of each step; in the record-fed day the rule changes nothing. Wiring it needs: (1) a per-type (JM, IM) PBL carry (u v t q e cm ch cq ipbl) kept on device or host, filled from the substep-2 PBL outputs of `jax_surface` (`r2['pbl']`, `pbl_li`, `pbl_land`, currently dropped after the step; only `aux['r2']['land']` is kept), (2) `begin_step` donor logic at the start of the step from OUR tile set, (3) overwriting the template columns 50:89 and 33:35 of the substep-1 rows (`jax_surface.build_template` slots) from the carry, (4) the leftover `dskin/khs/z0m` shift noted in D191. It changes the result of a record-fed day (our PBL outputs are not the recorded ones), so it cannot be validated bitwise against the records after step 0, only as a new, chaotic trajectory; it is only meaningful together with a template builder that no longer reads tile sets from the records (D174: tens of hours). I did not implement it; estimate of the wiring alone 4-8 focused hours (judgement, not measured). Not run: any wired JAX version, any other date for the census, a dec01/jan01 count of appearances.
