## 1. What the real model calls for radiation in P2SAoM40

### 1.1 Compile-time structure
- Rundeck `P2SAoM40.R:19-20` defines `USE_PLANET_RAD` and `GISS_RAD_OFF`; the component list (`:Components`) includes `socrates`; objects `planet_rad planet_alb lw_control sw_control` are linked.
  `GISS_RAD_OFF` compiles out the classic GISS radiation: `RAD_DRV.f` has ~20 `#ifdef/#ifndef GISS_RAD_OFF` sites (e.g. 278, 320, 2411, 2518, 2776, 3287, 3566-3599, 3623-3649, 4840 "skip for SOCRATES - too expensive");
  in RADIA the layer inputs become simply `SHL(L)=Q(I,J,L)`, `TLM(L)=T(I,J,L)*PK(L,I,J)` (RAD_DRV.f:2776-2783: i.e. the radiation sees the dynamical Q and T directly, negative Q is reset to 0 *in the model state*, 2778-2780).
  Consequence: SOCRATES is the only radiation scheme that executes; classic `TAUGAS/GETCLD/THERML/SOLARM` in `RCOMPX` never run (already recorded in FULL_FIDELITY_PLAN.md:402-446).
- Dedicated clear-sky handling: with `cloud_rad_forc=1` (rundeck) RADIA sets `l_clear_lw = l_clear_sw = cloud_rad_forc > 0` (RAD_DRV.f:3731-3734 region) and the clear-sky fluxes come out of the **same** SOCRATES call
  (`SRDFLB_CLEAR, SRNFLB_CLEAR, TRNFLB_CLEAR...`); the extra clear-sky/aerosol forcing `RCOMPX` calls (3566-3689) are `#ifndef GISS_RAD_OFF`. `aer_rad_forc=0`. So: **one `RCOMPX` (= one LW + one SW SOCRATES column) per column per radiation step.**

### 1.2 Call chain (verified by reading)
`MODELE.f` -> `atm_phase1` -> `RADIA` (RAD_DRV.f:1940-5501) -> per column `CALL RCOMPX` (RAD_DRV.f:3737) -> inside `RCOMPX` (RADIATION.f:1696-1942):
`seth2o`, `getgas` (+`fpxscalegas`) [RADIATION.f:1824-1827], `get_volc_column` [1856], `GETSUR` [1868, ALBEDO.f:281-866], `GETEPS` [1886], `set_planet_alb_param` [1899], **`run_planet_rad`** [1900],
`get_planet_radout` [1908], `deallocate_planet_rad` [1928]. `init_planet_rad` (reads spectral files, solar spectrum, aerosol optical tables; calls `init_planet_alb`) is called once from RADIATION.f:888.
`run_planet_rad` (planet_rad.F90:503-663) does, for LW always and SW only if `cos_zenith > 0.001` (`tol_cos_zenith`, `l_lit`): `set_t_level`, `set_control_lw/sw`, `set_dimen`, `set_atm`, `set_cld`, `set_aer`, `set_bound_lw/sw`, `set_major_abs`, then
**`radiance_calc(control, dimen, spectrum, atm, cld, aer, bound, radout)`** - the SOCRATES entry point (the only library routine named at this level; everything else are ROCKE-3D `planet_rad.F90` helpers that fill SOCRATES derived types).
Unlit columns get SW fluxes set to zero.

### 1.3 Inputs (what must exist per column on a radiation step)
Confirmed by reading:
- Grid/vertical: 43 radiation layers = 40 model layers + `LM_REQ=3` radiation-only layers above the model top (`npd_layer = lm_gcm + lm_req`, planet_rad.F90); `p_level(0:43)`, from `PEDN` for L<=LM+1 and `plb0` for the 3 top layers (RADIATION.f:1834-1835 pattern in `getgas` call; `RQT` temperatures of the top layers are *state*, updated each radiation step, RAD_DRV.f:5455-5463).
- Thermodynamics: `T*PK` (TLM) and `Q` of the 40 layers, `RQT` (3 layers), surface temperatures per tile type (`atmocn/atmice/atmgla/atmlnd%GTEMPR`, `atmsrf%TsAvg`).
- Clouds: RADIA masks and then converts `CLDSS, CLDMC` with `TAUSS, TAUMC` (the mask at RAD_DRV.f:2611-2615 is already ported and *changes the carried CLDSS/CLDMC*, ATM_STEP_PLAN section 7); optical depth/size assembly into `TAUWC/TAUIC/SIZEWC/SIZEIC` and cloud fractions at RAD_DRV.f ~2800-3160 (names seen by grep: `RDSS, RDMC, FSS, RHSAV, CLDSAV, QCL`; **body not read**). `planet_rad` module state: 15 length-43 arrays (`w_cloud_l, frac_st/cnv_water/ice_l, mix_ratio_*_l, dim_char_*_l, frac_area_st/cnv_l`), `cld_scaling`, `tot_cloud_cover`; `CLDEPS(43)` heterogeneity from `GETEPS` (static climatology lookup `cloud.epsilon4.72x46`, `KCLDEP=4`, FULL_FIDELITY_PLAN.md:459-464).
- Gases: `ULGAS(43,13)` column amounts from `seth2o/getgas` (rundeck: `GHG` file with `master_yr=1850`, `H2ObyCH4=1`, ozone `O3file` + `Ox_ref`, `dH2O` file) - time-dependent through day/year only.
- Aerosols: effectively off for this rundeck except volcanic (`MADVOL=2`, `RADN7=STRATAER.VOL.1850-2014_CMIP6_hdr`, `volc_yr=-1`); `MADAER=MADDST=0`, `NTRACE=0` (FULL_FIDELITY_PLAN.md:451-458). Note `TAero_*`/`DUSTaer` files are listed in the rundeck data section; whether any is read under this build was **not verified**.
- Surface: `PRNB(6,4), PRNX(6,4)` (diffuse/direct SW albedos for 4 surface types) from `GETSUR`, which needs the ~25 surface-state inputs listed in FULL_FIDELITY_PLAN.md:466-474 (fractions, per-type temperatures, snow/ice amounts, `PVT(12)`, wind `WMAG=atmsrf%WSAVG`, `COSZ`, `SNOAGE(3)` (RAD_DRV.f:3320-3322)), `frac_*`, `t_rad_*`, `snow_depth_*`, `soil_wetness`, `wind_speed_mag`.
- Orbit/star: `cos_zenith` (mean over the full radiation interval, `calc_zenith_angle(modelEclock, NRAD, cosz2, cosza)` RAD_DRV.f:2511), `solar_irrad = solar_constant/RSDIST` (RAD_DRV.f:2513-2514; `solar_constant = 1360.67` default in planet_rad.F90, not overridden in the rundeck namelist I read), `solar_spec='sun'` (`ModelE_Support/stellar_spectra`),
  `spectral_file_lw='sp_lw_ga7/sp_lw_ga7_dsa'`, `spectral_file_sw='sp_sw_ga7/sp_sw_ga7_dsa'`, `aer_opt_prop_lw/sw` (`aer_lw_ga7.nc`, `aer_sw_ga7.nc`), `aer_opt_prop_diag`. Directories are **hardcoded absolute paths** in `planet_rad.F90` (`dir_solar_spec`, `dir_spectral` -> the original ModelE_Support tree; read-only access is enough). Planet constants (radius, gravity, rotation) are Earth's (GOAL.md); `orb_par` defaults used (no override seen).
- ModelE's own "radiation-only" input list (RAD_DRV.f:2470-2487, `dimrad_sv = IM*JM*(7*LM+3*LM_REQ+24)`): `T, RQT, TsAvg, Q, P, CLDinfo(3 fields), rsi, zsi, wsoil, wsavg, snowi, snow, snowe, snoage(3), fmp, flag_dsws, ltropo, fr_snow_rad(2), dlake, flake`. **This `kradia>0` replay path is unusable here**: RAD_DRV.f:2758-2761 calls `stop_model('kradia > 0 not supported when using planet radiation')`. It is only useful as a hint of which fields radiation depends on (and it predates the tile `GTEMPR` arrays: the GTEMPR line is commented out in that list).

### 1.4 Outputs (what the rest of the model consumes)
From the code read: `SRHR(0:LM)`, `TRHR(0:LM)` (surface net SW/LW at index 0, heating rates `SRFHRL(L)`, `-TRFCRL(L)` at 1..LM; RAD_DRV.f:4441-4454); `SRHRS/TRHRS` for the 3 top layers (-> `RQT`);
`FSF(4,I,J)` (net SW at surface for ocean/ocean-ice/land-ice/soil from `FSRNFG(1,3,4,2)`), `TRSURF(4)`, `ALB(I,J,1:9)`, `SRDN, FSRDIR, SRVISSURF, DIRVIS, DIFVIS, DIRNIR, DIFNIR` (RAD_DRV.f:4517-4551), `CFRAC, RCLD` (3018-3021), `KLIQ`, TOA/surface flux diagnostics (`TRNFLB(LM+LM_REQ+1)`, `SRNFLB(...)`, clear-sky counterparts, `TRUPTOA/SRUPTOA/SRDNTOA`), and aerosol-diagnostic arrays when `TAero_aod_diag` (=2 in the rundeck).
Of these, only `SRHR/TRHR` (applied every step), `COSZ1`, the surface radiative fluxes (consumed by SURFACE/PBL/GHY/ice), `RQT` and `SNOAGE` feed the prognostic model; the TOA fluxes feed diagnostics only (the acc fields `srnf_toa`, `trnf_toa`, `incsw_toa`...). Note TOA fluxes are **not** in the current recorded set (`ffa_step_*_r` holds `SRHR,TRHR,COSZ1` only, 41x72x46 each) - needed for the F3 TOA diagnostics.

### 1.5 Cadence and state between radiation steps
- Cadence: `NRAD=5` source steps = 2.5 h (rundeck); the SOCRATES call happens only when `MODRD = MOD(Itime-ItimeI, NRAD) == 0` (RAD_DRV.f:2502; ATM_STEP_PLAN section 0). Between radiation steps RADIA jumps to label 900 and only does `T += (SRHR*COSZ1 + TRHR)*DTsrc*bysha*byMA/PK` (RAD_DRV.f:5474-5478) with **`COSZ1` recomputed every step** (RAD_DRV.f:2441 area: `CALL CALC_ZENITH_ANGLE(modelEclock,1,cosz1)`, and ATM_DRV.f:220) and `SRHR/TRHR` frozen. So the diurnal cycle of SW heating is reproduced by the per-step `COSZ1` multiplying the frozen `SRHR` (which was computed with the interval-mean cosine, `COSZ2`).
- State carried (restart list, RAD_COM.f `new_io_rad`): `s0, rqt, kliq, srhr, trhr, trsurf, fsf, salb, fsrdir, srvissurf, fsrdif, dirnir, difnir, srdn, cfrac, rcld, snoage, srnflb_save, trnflb_save` (+ aerosol-diagnostic arrays); in the module but derived: `dirvis`. There is **no radiation prognostic memory beyond these arrays** (no hidden multi-step solver state in `planet_rad`: `run_planet_rad` re-derives everything from module inputs and `deallocate_planet_rad` is called at the end of every `RCOMPX`; I read that, but did not read every `set_*` body).
- Dumps already on disk (3 dates x 6 steps): `ffa_step_<it>_r` = full prognostic state + `SRHR,TRHR,COSZ1` (16 MB per step); surface-side radiative exports are only embedded in `ffp/ffs/ffl/ffg/fft` tile records (24 MB per step in total for nov26 33312).
- Cost: the plan states RADIA is 65.6 % of the Fortran runtime (FULL_FIDELITY_PLAN.md, Phase 2 text). With the measured real wall time (~3-4 s/step average: the 5-day run took ~16 min for 240 steps, PHASE0_LOG.md:44; the 12 acc files span 11:27-02:01 over 12 months, ~1.2 h/month) this **implies (derived, not measured)** ~10 s per radiation step, ~3 ms per column per call, ~100 s per model day, ~50 min per model month, single thread.

## 2. Options for radiation in a multi-step run

Common fact: even with radiation solved, today's chained step still records (a) the sea-ice/ocean/lake/land-ice surface state, (b) Ent exports, (c) CONDSE non-dynamic entry state, (d) PRECIP_* effects, (e) the SURFACE composites (ATM_STEP_PLAN section 3). So every "free-running" variant below is a **free-running atmosphere over a replayed surface** until the ocean/ice/land chains are closed with the atmosphere (that is F3, section 4). Radiation does not remove that limitation.

### 2.A Recorded radiation from a longer instrumented real run, replayed open loop
- What: re-run the real instrumented model from a restart for 48 steps (1 day) or more with the existing `ffas`/`ffc`/`ffp`.. hooks (window length and `it0` are parameters of `ffas_on()`, ATM_DRV_atmstep.f.patch:23-39; whether the other hooks' windows are equally easy to widen was not checked), and feed `SRHR/TRHR` (every 5th step) and `COSZ1` (every step) plus the surface radiative exports to the existing `atm_step_fast.run_chain`.
- Dump size: the chain-needed set today is ~320 MB per step (ffa a/e/r 96 MB, ffc_cse_in/out 164 MB, tile records 24 MB, state 34 MB; measured on nov26 33312) -> **~15 GB per model day**, ~460 GB per month if nothing is slimmed. A radiation-only hook (new patch) needs only `SRHR,TRHR` (2.2 MB), `RQT`, `FSF(4)`, `TRSURF(4)`, `ALB(8)`, `SRDN,FSRDIR,SRVISSURF,DIRVIS,DIFVIS,DIRNIR,DIFNIR`, `SNOAGE(3)`, `CLDSS/CLDMC` mask effect, TOA fluxes: ~5 MB per radiation step, i.e. **~50 MB per day, ~1.6 GB per month**, plus 26 KB/step `COSZ1`. The rest (surface tile records etc.) is the cost of the *surface* replay, not of radiation. Disk: /panfs has 2.0 PB free; not a constraint.
- Validates: the radiation glue (heating applied to T, surface-flux consumption by the tiles, the RADIA cloud masking and `RQT/SNOAGE` updates), and dynamics+clouds+surface for 48 steps on a realistic radiative forcing; the divergence curve (section 3) with identical forcing; the F2 "one-day" rung for the atmosphere.
- Does **not** validate: any cloud-radiation or surface-albedo feedback (the recorded SRHR/TRHR respond to the *real* trajectory's clouds and temperatures, not ours); radiation itself; the TOA budget; and it is *biased for multi-week runs*: recorded real-model radiation acts like nudging towards the real cloud field (an open-loop forcing correlated with the real weather), which artificially reduces the divergence and makes any statistical comparison over a month invalid. Acceptable for <= 1-2 days; do not use for F3.
- Feasibility: high. Effort ~8-12 h (details in section 5). Risks: window parameters of other hooks; disk write time; libimf requirement for bitwise dynamics (existing D113/D126 caveat); first-step vs later-step surface records for k>=6 exist only if re-dumped.

### 2.B Call SOCRATES as a black box
Findings on how it is built (read): `model/socrates/libsocrates.a` (2.07 MB, 138 `.o` files) is a **static archive built with ifort 19.1.3**, flags from `config/compiler.intel.mk` (`-fpp -O2 -ftz`, release `-assume protect_parens -fp-model strict -fp-speculationoff`), **not `-fPIC`** (confirmed 2026-09-27 in PHASE0/plan: `ifort -shared --whole-archive` fails on ~40 objects). It is Fortran 90 with derived types (`def_atm, def_cld, def_aer, def_bound, def_control, def_spectrum, def_out`), no `BIND(C)`.
Source for a recompile is at `ModelE_Support/socrates/src` (subdirs `radiance_core, modules_core, modules_gen, correlated_k, scatter, radiation_control, general, aux, um`) with the Makefile `model/socrates/Makefile` listing `Mk_mod_gencore/Mk_src_gencore/Mk_src_radcore`; plus `def_planetstr.F90` and the `interface` dir. `ModelE_Support/socrates/make` has `Mk_cmd_ifort`, `Mk_cmd_gfortran`; gfortran 12.1 and mpif90 (Intel MPI) are on this node (`env_modele.sh` gives ifort 19.1.3). Building SOCRATES itself is thus feasible in a scratch copy (copy, never edit the original).

The boundary (where the "thin wrapper" sits) is the decision, and it is *not* the SOCRATES API:

- **B1: boundary at `run_planet_rad`/`get_planet_radout`** (what the first plan assumed). Python (or a small Fortran shim) must fill ~60 module variables per column and then call the two routines. Exact interface:
  `run_planet_rad(iup_h2o,iup_co2,iup_o3,iup_o2,iup_no2,iup_n2o,iup_ch4,iup_cfc11,iup_cfc12,iup_xghg,iup_yghg,iup_so2, ULGAS(43,13), CLDEPS(43), PRNB(6,4), PRNX(6,4))` plus module state `p_level(0:43), t_layer(43)[or t_level(0:43)], w_cloud_l, frac_st_water_l, frac_st_ice_l, frac_cnv_water_l, frac_cnv_ice_l, mix_ratio_{st,cnv}_{water,ice}_l, dim_char_{st,cnv}_{water,ice}_l, frac_area_st_l, frac_area_cnv_l, cld_scaling, cos_zenith, solar_irrad, wind_speed_mag, frac_sea/land/sea_ice/land_ice, t_rad_*, soil_wetness, frac_veg_tbl(n_veg), frac_land_snow_tbl(2), snow_depth_land_tbl(2), snow_depth_sea_ice, snow_amnt_sea_lake, aer_mass_div_dens(50,43), aer_component, rel_humidity(43)...`; outputs via `get_planet_radout(TLB,TLT,NORMS0, TRUFLB,TRDFLB,TRNFLB,TRFCRL,*_CLEAR, SRUFLB,SRDFLB,SRNFLB,SRFHRL,*_CLEAR, FSRNFG, SRIVIS,...,SRXVIS,SRXNIR,S0, TRUPTOA,SRUPTOA,SRDNTOA, aesqex,aesqsc,aesqcb)`.
  The catch: everything that *produces* these arguments is ModelE glue, not SOCRATES: `getgas/seth2o/fpxscalegas` (gas columns, GHG/ozone files), `get_volc_column/getvol`, `GETSUR` (~585 lines of albedo logic), `GETEPS`, RADIA's cloud-property assembly (~400 lines, not read) and RADIA's post-processing (~800 lines, 3740-4560, not fully read) which makes `SRHR/TRHR/FSF/...` from the SOCRATES output. To call `run_planet_rad` from Python one must **re-implement that glue** (~2,000+ lines of non-SOCRATES ModelE code). That is allowed by the constraint (it is not SOCRATES) but is the bulk of the work: ~40-80 h and is itself a validation burden (it can be validated against the recorded `SRHR/TRHR` and the `ALB` arrays at ~1e-12 since the same binary SOCRATES is called). Not recommended as the first step.
- **B2: boundary at `RADIA` itself, inside a real-ModelE-linked "radiation server"** (recommended; this merges B and D in the cheapest way). Build a scratch copy of the model tree with a patched main loop (the same way the instrumented binaries are built, PHASE0_LOG.md:87: "built in a scratch copy in ~1 min") in which, instead of stepping, the program (i) initialises ModelE normally from a real restart (this loads GHG, ozone, volcanic, `GETEPS`, spectral files, surface/vegetation boundary conditions, orbit), (ii) loops: reads a binary state packet from a FIFO or file written by Python, overwrites the module arrays RADIA reads, forces `MODRD=0` for that call, calls the real `RADIA`, writes the output packet. All ModelE glue stays real Fortran, SOCRATES stays a black box, state marshalling is flat binary arrays (like the existing `read_cse` record format, `name,rank,n(1:4),data`), no `ctypes`, no `-fPIC`, no MPI-in-a-shared-library problems, no Python port of GETSUR/getgas. The proof-of-concept `fullfidelity/socrates_poc` already established the subprocess architecture with the same ifort 19.1.3 toolchain, so only the program is larger.
  Packet in (per radiation step; sizes for 72x46): `T,Q,QCL,QCI` (40 layers), `PEDN/P` (41/1), `RQT` (3), cloud carry `CLDSS,CLDMC,TAUSS,TAUMC,SIZESS,SIZEMC` (+ whatever else the RADIA cloud block reads: **exact list must be taken from RADIA 2555-3160**; not read here), per-tile surface temperatures `GTEMPR(4)` and `TsAvg`, `WSAVG`, `RSI, ZSI`, snow fields (`snowi, atmgla%snow, atmlnd%snowe, fr_snow_rad(2)`, `SNOAGE(3)`, `fmp`), soil wetness, lake depth/fraction, `ltropo`, land/ocean/ice fractions; calendar (`Itime`) for zenith/ozone/volcanic. About 80 MB if everything is 3-D 8-byte (7*LM+... per the `dimrad_sv` count: IM*JM*(7*40+3*3+24) = 3312*313 = ~1.04 M doubles = 8.3 MB) - small.
  Packet out: `SRHR(0:40),TRHR(0:40)`, `SRHRS/TRHRS(3)`->`RQT`, `FSF(4),TRSURF(4),ALB(8),SRDN,FSRDIR,SRVISSURF,DIRVIS,DIFVIS,DIRNIR,DIFNIR,CFRAC,RCLD,KLIQ`, modified `CLDSS/CLDMC`, `SNOAGE`, TOA fluxes (`SRNFLB(LM+LM_REQ+1)`, `TRNFLB(...)`, clear-sky, `incsw_toa`...). ~4.5-9 MB.
  State RAD_COM carries between radiation steps (the list in 1.5) must be in the server's memory: the server persists across calls, so `snoage`, `rqt`, etc. are held there or exchanged; Python must treat `SNOAGE`/`RQT` as state of the *atmosphere* (RADIA modifies them) and pass them in/out so the two sides cannot diverge.
  Hazards: (1) module state that RADIA reads but that the server's initialisation sets from the restart (anything not in the packet silently stays at its restart value: audit by running the server on a real restart with real step-0 state and checking bitwise `SRHR/TRHR` against the recorded `ffa_step_33312_r` - this is the built-in oracle); (2) MPI/ESMF initialisation of the full ModelE init in a stand-alone main (ModelE is built with `MPI_Support`; run with 1 rank); (3) cost of ~10 s per radiation step single-threaded (derived), 3312 columns, no OpenMP directives found by grep in RAD_DRV.f (`$OMP` count 0), so parallelism would only come from MPI lat-band decomposition (not scoped); (4) it is Intel-libimf-numerics identical to the real run (same binary objects) - an advantage: radiation is bitwise reproducible against the dumps.
- **B3: ctypes/cffi `.so`**. Needs everything linked into the shared object to be `-fPIC` (SOCRATES from source, plus the ModelE RAD/ATM modules if the boundary is RADIA), plus a model initialisation inside a shared library (global state, MPI init). Possible but strictly more work than B2 for no benefit here (the call crosses once per 2.5 model hours). Not recommended.

### 2.C Pre-computed radiative-transfer emulator
Not recommended. It would be a statistical surrogate, so it can never satisfy the stated F1-F3 meaning ("matches the real model", GOAL.md; ledger style "recorded input" or exact), the training set (several model days of columns from the real run) is itself the dump set of option A at larger scale, and the surrogate error would be confounded with the chaos-aware comparison (a systematic radiative bias of 0.1 W m-2 is of the same order as the monthly-mean diagnostics we want to compare). Only justified as a *speed* product after the exact path exists (GPU radiation), where SOCRATES-on-CPU would dominate runtime. Effort if ever done: 60-150 h (judgment).

### 2.D Real Fortran radiation in the loop via files
Same idea as B2 in a cruder form (Python writes state files, launches the instrumented binary which restarts, runs RADIA and exits). Each radiation step would pay the model start-up (reading restart 187 MB, init) + a model step; ~30-60 s per radiation step (judgment) and needs a restart-writer from Python (the 257-variable restart; `compare_restarts.py` knows the layout). B2 keeps the process alive and avoids the restart. D is a fallback if B2's patched main loop proves hard.

### 2.5 Recommendation and first-task plan
Recommend **A for the next one-day milestone, then B2 (radiation server linked from real ModelE objects) for anything longer; skip B1/B3/C**.
First tasks, in order (all in scratch copies; no edits to the original tree or existing repo files):

## 3. Validation protocol that respects chaos (F2 / F3)

### 3.1 What chaos does (measured, existing)
- D3 (ledger, 5 days, real Fortran, +-1 ulp in T everywhere): T layer 1 pointwise RMS 0.048 K (field std 2.74 K), global-mean difference 1.4e-4 K, zonal-mean RMS 0.007 K; U RMS 0.36 m/s; whole-column T RMS 0.27 K (max 5.5 K), U/V RMS 0.74 m/s, p RMS 0.33 hPa; only 36 of 257 restart variables bitwise equal. Pointwise equality is therefore impossible beyond ~hours, and the *noise floor* is: pointwise a few % of field variability, global/zonal means ~1e-3-1e-2 of it, after 5 days.
- D134 (ours vs real, 6 steps, libimf): step 0 at rounding level (<= 2e-12 of scale); at CONDSE of step 1, 157-209 *new* columns jump to ~1e-2 relative error (threshold flips), then spread; end of step 5: T rel 9e-5-3.6e-4, Q 7e-3-6.4e-2, U 2.5e-3-1.3e-2. Consistent with D3's chaos (not a bug). In libm mode (numpy pow) the flips begin at step 0 in 3-4.6 % of columns.
- Real model is bitwise deterministic for identical input (PHASE0_LOG.md:42-55): perturbation of one ulp is the *only* source of noise in a real-vs-real comparison, which is exactly the right model for "port differs from real only by rounding + threshold flips".

### 3.2 Proposed protocol (all thresholds below are proposals to be fixed *before* looking at port results; none is an existing project decision)
Stage S0 (cheap, ~1 day of real runs): **divergence-curve overlay.** Run the real model from the same restart with `n_real = 6-8` perturbed members (T +-1 ulp, optionally also +-1 ulp in Q or U with different random seeds) for 48 steps (1 day), writing the full prognostic state every step. Compute for each field group (T, Q, U, V at layer 1, 5, 21; whole-column RMS; PEDN/p) the RMS difference between member pairs vs. step k (1..48). The band between the min and max member-pair curves is the **real noise floor curve** `N(k)`. Run the port from the unperturbed restart (open-loop radiation, option A, or B2) and compute the same RMS difference vs the unperturbed real state, `P(k)`. Acceptance: `P(k)` lies inside `[0.5 N(k), 2 N(k)]` for the quantities above at k = 1..48, *and* global-mean and zonal-mean differences are within the real ensemble band. Rationale: a port at rounding level is statistically one more ensemble member; if it is slower or faster to diverge than the real members, something systematic differs (a bug or a missing process). It requires no pointwise match.
Stage S1 (5 days = D3 horizon, existing recipe): same with 240 steps, `n_real = 4-6`, port `n_port = 2-4` perturbed members (so the port's own spread is estimated, not assumed). Acceptance on global-mean and zonal-mean (46-lat) time series of T(layer1,5,21), Q, U, p_surf, and column-integrated energy diagnostics: `|mean_port - mean_realEns| <= 2-3 sigma_realEns` per quantity with a multiple-testing allowance; zonal-mean RMS vs the real ensemble mean `<= 1.5x` the real members' own RMS vs the same mean (leave-one-out).
Stage S2 (one month, F3): `n_real = 8` perturbed members of JAN (start `fort1_jan01_itime17520.nc`; 1488 steps; 31 days: IDACC[0]=1488 in the JAN1950 acc file) -> monthly means. The existing `JAN1950.accP2SAoM40.nc` is the *unperturbed* real member (bitwise reproducibility of a restarted segment was shown for 5 days, PHASE0_LOG.md:42-55; for a month it has not been demonstrated: check `1JAN1950.rsfP2SAoM40.nc` -> a re-run from the jan01 restart reproduces JAN1950.acc, 1 real month ~1.2 h, as the first oracle test). Diagnostic fields below; metric per field: global mean, 46-point zonal mean (and optionally gridpoint monthly mean), port minus real-ensemble-mean, in units of real-ensemble standard deviation; pass if >= ~95 % of zonal bins lie within 2 sigma (and none beyond 4), plus a port-ensemble spread ratio in [0.5, 2]. The noise floor is *defined* by the real ensemble: its monthly-mean sigma per field is the acceptance threshold, not an arbitrary tolerance.
Important: only the 5-day floor (D3) is measured today; **the 1-day curve, the 1-month ensemble floor and the rate at which the real model's monthly means differ between members are not measured**. Spin-up caveat: the acc files come from a run started cold (ISTART=2, 1 Dec 1949; rundeck `&INPUTZ`), so Jan 1950 is still spin-up weather/climate; the comparison is port-vs-real from the *same* restart, so spin-up is not a confound.

### 3.3 The 12 monthly acc files (read)
`ModelE_Support/prod_runs/P2SAoM40/{DEC1949, JAN..NOV1950}.accP2SAoM40.nc`, 54.2 MB each, plus `PARTIAL.acc` and `SEP1950`. Dimensions of JAN1950: `aij` 1660 fields x 46 x 72 (accumulated lat-lon maps; includes pressure-level `t_/q_/z_/u_/v_/omega_/rh_` x 20 levels, `slp, tsurf, tgrnd, sst, prec, evap, runoff, pcldt, clwp, pblht`, SW/LW surface and TOA budget terms `incsw_toa, srnf_toa, trnf_toa, srnf_grnd, trdn_surf...`, tile fractions, ice, snow, soil, lake), `aijl` 24 x 40 x 46 x 72 (`temp, q, rh, cf, wtrcld, icecld, wtrtau, icetau, QLrad, QIrad, z, airmass`), `aijk` 15 (`dpb, ub, vb, dse, tb, w, UxV,...`), `aj` (9 types x 85 x 46 budget), `ajl` (81 x 40 x 46 zonal-mean profile diagnostics), `asjl`, `consrv` (170 x 46 conservation quantities), `adiurn`/`hdiurn`, `isccp` histograms, `idacc` (counters per accumulation class: 1488, 298 [= radiation calls, 1488/5 rounded up], ...), `scale_*`, `denom_*`, `ia_*` (which counter divides each field). The monthly means are `aij/idacc[ia]*scale` (and `denom` division for weighted fields); I did not read DEFACC/DIAG code, so the exact scaling per field must be read from the nc metadata + DEFACC.f for each chosen field.

### 3.4 Minimal diagnostic set our port would need (none of AIJ/ADIURN is ported)
Proposal, to be ranked after reading each accumulation in DIAG.f/DEFACC.f (none verified yet): compute directly from the model state each step in Python (instead of porting DIAGA/DIAG5A etc.), accumulate over the month, and compare to the acc means:
 1. Global/zonal state means: `tsurf` (surface air T), `tgrnd`, `slp`, `prsurf`, `qatm`, `t_850/500/200`, `z_500`, `u_200`, `usurf/vsurf/wsurf`, `pblht` (from `aij`); `temp`, `q`, `cf` (`aijl`, zonal-mean profiles).
 2. Moisture budget: `prec, evap, prec_mc, clwp, pcldt` (cloud/convection outputs are ported; `pcldt` needs the `CLDSS/CLDMC` column cover logic of the accumulation).
 3. Radiative budget: `incsw_toa, srnf_toa, trnf_toa, srnf_grnd, trdn_surf`: need radiation TOA and surface flux outputs (recorded in A or returned by B2; **these are not in the current dumps**).
 4. Surface/ocean: `sst`, sea-ice `sivol/simass`, `runoff_soil`; from the ocean/ice chains once closed.
 5. Energy/mass conservation `consrv`-type global means: dSE/dKE terms (`dSE_Dyn` etc.).
 About 25-30 `aij` fields + 4 `aijl` + zonal means from `aijl/ajl`. Validation of our diagnostics themselves: run the real model for 1 day from a restart with acc output (a `PARTIAL.acc` file shows partial accumulations are written at the end of a run, in `prod_runs`), feed our diagnostic code the *real* per-step states (the `ffa_step_e` dumps) and compare to that 1-day acc: deterministic, no chaos. This is the cheap way to validate the diagnostics before they are used in chaos-aware comparisons.

### 3.5 Compute needed (at measured speeds; CPU only, no GPU on this node)
Per step, port: dynamics ~1-3 s (D141/D144b: chained JAX dynamics ~2.7x faster than numpy), clouds ~5 s (batched; not yet wired into the joined step), surface ~1 s, filter ~0.5 s, ocean ~4 s => ~12-14 s/step (D134 measured 9-16 s per step for the numpy-batched chain without ocean; ocean time from the task statement). Black-box radiation: ~10 s per radiation step (derived) = 2 s/step amortised.
- 1 day (48 steps) per port member: ~10-11 min (~13 s/step incl. radiation amortised: ~11 min).
- 5 days: ~55 min per member; 4 members ~3.7 h serial.
- 1 month (1488 steps): ~5-6.5 h per member; 4 port members ~22-26 h serial (JAX/numpy scaling over the 12 cores was not measured, so no parallel estimate is claimed).
- Real model: ~3-4 s/step single thread: 1 day ~3 min, 5 days ~16 min, 1 month ~1.2-1.5 h per member; an 8-member real ensemble of one month ~10-12 core-hours (independent processes; 12 cores available), ~1.5-2 h wall if all run in parallel on this node (memory per run not checked).
- Disk: per-step full-state output for S0 (8 members x 48 steps x ~35 MB) ~13 GB; fine.
