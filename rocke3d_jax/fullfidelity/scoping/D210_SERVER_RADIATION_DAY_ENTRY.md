## 1. How the server is driven (demonstrated by running it)
* Infrastructure used as is: `Phase1.radia` -> `jax_radiation.make_handoff_step` -> `RadiationHandoff.io_callback(ordered)` -> `PersistentServer.request` (packet file exchange, FIFO control). Only `d210_day.py` (copy of `d209_day.py`) sets `Phase1.rad_mode='server'` after `Coupled` setup, starts the server (about 16 s), and swaps the live packet per radiation step.
* Cadence: `NRAD=5` in the rundeck; radiation steps are `(itime-ITIMEI)%5==0`: 11 calls in the 54 steps (it 33312, 33317, ..., 33362; the last is after the day boundary at 33360, the server crossed it without problem). On the other 4 of 5 steps there is no call; the HELD server SRHR/TRHR (verified equal between consecutive steps in the records) are applied with the per-step COSZ1, as RADIA does. Held: SRHR, TRHR (and all other server outputs, RQT, KLIQ, SNOAGE, FSF, ...).
* What the packet contains: atmosphere (T, Q, PK, PMID, PDSIG, PEDN, MA, LTROPO), the 19 cloud arrays, SNOAGE (CONDSE exit of OUR chain) all from OUR device state; RQT and KLIQ from the server's own previous output (first call: live packet of step 0). RECORDED inputs (named, not computed): (i) the 21 surface fields of the packet (RSI, ZSI, SNOWI, POND_MELT, FLAG_DSWS, FLAKE, DLAKE, FLICE, FLAND, FEARTH, GTEMPR1-4, TSAVG, WSAVG, SNOWLI, ZSNOWI, BARESW, FRSNOW, SNOWD) read from the real model's live packet `rsv_n26_<it>_in.bin` of that step (D185 practice), not from our ice/lake/land state; (ii) the RADIA random seed (recorded SEEDS[1]); (iii) COSZ1 on the four held steps (recorded `ffa_step_r`); (iv) at server start the restart of 33312. On a radiation step the server's masked CLDSS/CLDMC and SNOAGE are written back into the carry (existing `Coupled._writeback`).
* Cost: 11 calls, server request 151 s total (RADIA+IO 138 s, about 12.5 s each), callback total 166 s, 370 MB device->host, 128 MB host->device, 11 host sync points. Day wall 1653 s (steady step about 16 s; radiation steps about 31 s; step 0 about 465 s with 125 compiles). The server could be driven on 5 cores for JAX plus its own cores; no deadlock; no record dependency blocked it. The only record dependencies are the ones listed above.

## 4. Task 3: where the first difference from the replay-driven day appears (`cmp_s54.json`, `cmp_s6.json`)
* Step 0: T differs in 2 elements by 1.1e-13 (rms 3.6e-16); U V Q P QCL QCI bitwise equal. Cause: server TRHR vs recorded TRHR (15 elements, 1.1e-13, category B), i.e. the radiation call itself; SRHR bitwise.
* Step 1 (no radiation call): T 129114 elements differ, max abs 2.3e-3, U 1.3e-3, V 1.8e-3, Q 2.7e-5, but rms only T 8.8e-6, U 5.1e-6, V 6.6e-6, Q 1.1e-7 (0.01-0.08 of the largest member distance). In a 2-step diagnostic run with full arrays (`x2_*.log`; arrays not kept) the difference after the dynamics stage is still ~1e-13 (U 2.4e-13, T 1.1e-13) and becomes 1.8e-3 (U), 2.4e-3 (T) after CONDSE: the discrete convection/cloud branches amplify the 1e-13 perturbation locally. This is the same sensitivity the real model shows to a one-ulp perturbation (that is what the member noise floor measures); I did not prove that it is the identical mechanism, hypothesis.
* Growth of the server-minus-replay rms in units of the largest member rms(member-real): step 2 about 0.1-0.3, step 5 0.4-0.97, step 10 0.8-1.0, steps 20-53 about 0.9-1.06 (QCI 0.6-1.6). So from about step 10 the two trajectories are as far apart from each other as the five real members are from the real run: the server day is statistically a different but equivalent realisation.
* The radiation inputs of the server are of the same size as that divergence (section 2, rms 1.6e-2 to 9e-2 relative in the heating rates), so the effect of computing radiation vs replaying it on the day cannot be separated from trajectory noise with one day.
