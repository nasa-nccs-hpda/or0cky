## 1. What was built
`fullfidelity/gpu_step_run.py [DATE] OUTDIR [--steps N] [--ref NPZ] [--save all|first-last|last|none] [--steady-repeat R] [--timed] [--cpu-flags auto|on|off] [--io-audit]` and `--compare CAND.npz REF.npz [OUTDIR]` (stand-alone, numpy only).
- Runs `jax_coupled.Coupled` for N steps (default 1; the data subset covers 6) of nov26 from the recorded start state; the state pytree stays on the device between steps, only the records of the next step are uploaded.
- **libm wiring without editing a file:** `jax_coupled` imports `d187_imf_p1` and calls `W.install()` at import and `Coupled.__init__` calls `W.make_phase1` and `FX.set_mode('libimf')`, all of which hard-require libimf. Before importing `jax_coupled` the runner sets `libimf_ops` and `libimf_fused` to `libm`, replaces `W.install` by a no-op (no rebinding of the `jnp`/`conv_micro_j`/kit names: the original `jnp.power`/`jnp.exp` code of the D186 libm path stays), replaces `W.make_phase1` by a direct `jax_atm_phase1.Phase1(date, rad='replay')` (its own context is `imf=False`, `cf.set_backend('numpy')`, the pole columns run the NumPy port in libm), and makes `FX.set_mode` ignore the request for `libimf`. The run asserts `ctx.imf == False`, both modes `libm`, and records the number of libimf callbacks (0 in every step).
- **Every libimf path, checked by running with `INTEL_LIBIMF_DIR=/nonexistent_libimf`** (library absent: `intel_libm_ff.available()` False, so any hard dependency would raise) and `pytest`/`hydra`/`omegaconf` made unimportable: the complete 6-step run completed. Paths and their libm behaviour: dynamics `pow(PMID,KAPA)`, PGF, `PEK`, TROP, MAtoPMB (D186 modules: `jnp.power`), LSCOND (`'xla'` mode), the fused MSTCNV path D189 (`libimf_fused.fx` returns `jnp.exp/jnp.power` for every request in libm mode, no callback, no gcc shim), `libimf_ops` (`jnp` branch), J3 DISSIP/FILTER (`jax_phase2` uses `jnp.power` when `libimf_ops.mode() == 'libm'`), snow-age exp, `KitImf` (not installed). Nothing needed a libm fallback to be written; what blocked was only the three names above in `d187_imf_p1`/`jax_coupled`. The C shim of D189 is never built.
- **XLA flags:** `clouds_jax_env*` set the CPU flags only `if 'jax' not in sys.modules`. The runner decides first (`--cpu-flags auto`: CPU flags only if no NVIDIA device node/variable is visible or `JAX_PLATFORMS=cpu`); on a GPU it imports `jax` BEFORE any model module, which turns every later `import clouds_jax_env` into a no-op, then initialises the backend and prints `backend`, `devices` and the `XLA_FLAGS` actually in effect (warns if CPU flags are present on a non-CPU backend, or if a GPU node is visible but the CPU backend was found). `GPU_KEEP_ALGSIMP` is therefore irrelevant for this mode. Not testable here: that the GPU branch of the decision is taken on the cluster (only `--cpu-flags off` on the CPU backend was run, section 3).
- Host callbacks kept: MSTCNV QUS subsidence (176 calls, 249.5 MB through the host per step), two CONDSE pole columns, the 4 OADVT2 pre-pass calls, the replay hand-off `io_callback`. The callbacks are NumPy functions; no JAX operation is executed inside them. Whether the GPU backend runs `lax.cond`-guarded ordered `io_callback`s and `pure_callback`s inside long `while` loops without stalling is the open question of the first GPU run (the smoke test covered `pure_callback` inside jit only).
- Per step it records: wall seconds (block on the new state), jit executions, eager primitive dispatches, XLA compilation count and seconds, stop-model flags, libimf/QUS/pole/OADVT2 callback counters, and optionally per-stage times (`--timed`); backend, devices, versions of jax/jaxlib/numpy/netCDF4/scipy/mpmath (from the imported modules), core affinity, git head, `libimf_available_on_host`, `libimf_used: false`. End state arrays: `OUTDIR/<date>_libm_step<k>.npz`, 558 arrays at step 0 and 569 later (same keys as D191 `*_asm.npz`: `dyn/ condse/ radia/ surface/ dissip/ filter/ X/ surf/ land/`). With `--ref` (a `{k}` in the name = the step number) the in-script comparison prints categories A/B/C/D per group and in total, `max_rel` (max|diff|/max|ref| of the field) by category, the worst fields, and stores per-field rows (`rel`, point-wise relative maximum, number of differing elements and columns) in `result.json`.
- Needs in the container: numpy, jax(+CUDA), netCDF4, scipy, mpmath (all imported in the smoke job). Not needed: pytest, hydra/omegaconf, git (a failing `git rev-parse` gives `unknown`), gcc, libimf, the radiation server, the NumPy reference. At least 2 CPU cores.

## 2. Is the libm assembled step a faithful port? (new check, CPU)
The only new numerical configuration is libm mode (D191 ran with libimf). To separate "wiring error" from "libm differs from libimf", a NumPy libm reference of the same closed-surface chain was made (a scratch copy of `d187_ref_numpy.py` with `make_ctx(date, imf=False)`; step 0 of nov26, 199 s, not committed). The libm runner step 0 against it: **555 A, 3 B, 0 C, 0 D of 558 arrays** (the 3 B are `surf/lake/tlake` 5.6e-17, `mwl` 1.6e-23, `gml` 1.5e-23 relative; `land/p4_ij`, a static host index array, exists only in the reference). So the libm step is the NumPy libm chain to rounding level, as the libimf step was the NumPy libimf chain (D191 C1 = A). The NumPy libm reference against the NumPy libimf reference (D191 `ref/nov26_ref.npz`) gives 127 A, 170 B, 47 C, 215 D: the same split as the JAX libm run against the JAX libimf run (section 3), i.e. the libm/libimf gap is a property of the math library, not of the port.

Reading: in libm mode at step 0 about 200 of 558 arrays are category D against anything that is not the very same arithmetic: libimf (run A: 215), another XLA version (run D: 198), no CPU flags (run E: 208). These are the threshold fields (CONDSE sparse diagnostics such as `X/VKMSP`, cloud fraction and precipitation, PBL EGCM/W2GCM/PBLHT, and what the filter spreads from them), where a 1-ulp change flips a branch in some columns (e.g. `filter/T`: max 0.012 K in 3,312 columns after the filter; `X/PREC` 29 columns; `filter/P` 3e-8 relative in 138 columns). The **dynamics stage is the clean indicator**: libm vs libimf B/C, max 1.7e-11; JAX 0.5.3 vs 0.6.2: bitwise. A GPU result must therefore be expected at C/D in the same fields and cannot be called "wrong" from a D count alone; the statistical noise-floor view of ACCEPTANCE section 4 is the way to judge it, and a single run proves only that the step executes, its timing and where it lands at rounding level.
