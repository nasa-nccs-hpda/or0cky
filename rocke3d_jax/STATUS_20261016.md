## 5. The parallel runner (task 6) and its first full run

`gpu/run_variants.sh` submits one SLURM job per variant (two exclusive V100 timing pairs of Fortran x3 then JAX on the same node, 108 steps; two 54-step fidelity runs; the sharded regression with the speed flags off and on) plus a summary job that runs after all of them end and writes `SUMMARY.md` through `gpu/summarize_variants.py`. Required environment variables are listed at the top of the script. Two full runs on 2026-10-17: `variants_20261017_c` (commit 50b23ff for the test jobs) and `variants_20261017_d` (commit aa3cc61), the second to measure repeat spread. Both pairs landed on the same nodes (gpu011 release, gpu012 fast) both times.

Results (two runs; not bitwise repeatable):
* Fidelity, worst ratio at steps >= 3, run c / run d. Release: T 1.18 / 1.18, U 1.24 / 1.24, V 1.24 / 1.24, Q 1.15 / 1.15, P 1.22 / 1.22, QCL 1.58 / 1.58, QCI 2.37 / 2.37 (identical to two decimals in both runs). Fast: T 1.12 / 1.05, U 1.13 / 1.09, V 1.09 / 1.05, Q 1.06 / 1.05, P 1.19 / 1.04, QCL 1.60 / 1.59, QCI 2.47 / 2.47. So the fast configuration varies between repeats by up to 0.15 in P, while QCI at step 3 stays at 2.47 and the strict 2x rule is not met in either configuration. The earlier fast run (1.04-1.07 on T, U, V, Q, P) lies inside that range.
* Timing: Fortran 252-256 s wall per 108-step run (whole process, about 2.35 s/step upper bound). JAX median step after the first, run c / run d: release 1.72 / 1.70 s (gpu011), fast 0.78 / 0.79 s (gpu012); Fortran 251-256 s on both. The repeat on the same nodes agrees to about 1%, so the 0.78 s is stable on these nodes. The archived fast figures are 0.524 s/step (matched) and a 0.385 s held step. The difference is not explained: the archived numbers were measured on other nodes with an older recipe, and the statistic (median of steps 1+ here) may differ. Do not quote 0.78 s against 0.524 s until that is settled.
* Regression subset, run d: 3285 passed, 0 failed, 43 skipped in both configurations (run c, without the two isolated files: 3279 passed). The 3 extra skips against the reference's 40 are `test_ent_ff.py` tests that skip when `MODELE_SRC` is unset; a probe job with it set gave 7 passed, 1 skipped instead of 4 passed, 4 skipped, so the runner now exports it (not yet re-run in full; expected 3288 passed, 40 skipped). `test_jax_state` collects no tests (rc=5), as before.

What the first runs taught (all fixed in the script, none in the model code):
* `MODELE_PROD_INPUT` must be the complete `ModelE_Support/prod_input_files`. The in-repo `modelE2_planet_2.0` directory is partial (it lacks `S72x460098M.ext.nc`), which is enough for the 6-step gate but not for the day runs. A secondary error in `d193_day.py` (`hp.calls` on `None`) hides the real one when a run fails early.
* The Fortran timing runs need only the production binary `huge_space/P2SAoM40/P2SAoM40.bin` and its run files, not `fullfidelity/instrumentation/`: both pairs ran. This closes that open question for the timing runs; whether the reference data itself can be regenerated from it was not tested.
* Tests need `XLA_FLAGS` (as `run_all_tests.sh` already says), `JAX_PLATFORMS=cpu` when a job without a GPU lands on a GPU node, and NumPy's AVX-512 paths off on the Xeon Gold nodes: with them on, NumPy `pow` differs in the last bit and 65 bitwise tests fail (probe: 83 tests, 16 failed with AVX-512, 0 without). The tests were written on a non-AVX-512 host. The JAX runs on the same nodes use host NumPy too; whether that moves the fidelity ratios was not tested.
